# 题库导入与大模型辅助 · 设计与答辩口径

> 另见：`docs/xiaozhi-rag.md`（小智 AI 智能体 —— 同一后端代理的 RAG 问答路线）。

## 1. 导入流程与选型建议

**流程**：下载模板 → 批量上传 CSV/Excel（或逐题录入）→ **待确认列表** → AI 辅助检查（建议）→ 管理员逐条确认/修改 → 确认入库（唯一写入入口）→ 抽题索引与星图同步更新。

| 决策点 | 选择 | 理由 |
|---|---|---|
| 批量格式 | **CSV 为主，Excel(.xlsx/.xls) 兼容** | CSV 零依赖、带 BOM 模板 Excel 打开不乱码、可用任意编辑器生成；Excel 通过动态加载 SheetJS 支持（不进主 bundle），照顾命题组现有 Excel 习惯 |
| 导入后 | **待确认列表，不直接入库** | 批量数据必有脏行（缺字段/章节错误/公式残缺）。直接入库会污染做题闭环；待确认列表让错误行"待补充"标记可见、可改、可删，且**不阻塞**其他完整行 |
| 工作台形态 | **全屏工作台**（区别于做题浮层） | 批量审阅是高密度编辑任务，需要列表+编辑表单双栏；做题是单任务流，用居中浮层不打断星图语境。两种形态各按任务密度选型 |
| 小批量补充 | **逐题录入表单** | 与批量导入共用同一题目形状、同一套完整性检查与确认流程，无第二套逻辑 |

模板列：`题干、选项A、选项B、选项C、选项D、答案、解析、章节、难度、关联考点`。
兼容合并列「选项」（`A.xx|B.xx|…`）；选项全空自动识别为填空题，答案列写可接受答案；章节列接受章节名或 id；关联考点用 `;` 或 `|` 分隔。

## 2. 大模型选型：DeepSeek（deepseek-chat）

- **国产合规**：大赛指定国产大模型方向，DeepSeek 为国产开源模型代表，符合赛事要求；
- **数学推理见长**：数学题归类/公式格式判断正是其强项场景；
- **工程成本低**：OpenAI 兼容接口，代理骨架 100 行即可接入；质检是轻量任务，`deepseek-chat` 足够，无需 R1 推理模型（更慢更贵）；
- **temperature=0 + JSON 强制输出**：建议结果稳定、可复现、可解析。

通义千问同为可选（代理只需换 upstream 与 Key），选 DeepSeek 的核心理由是数学场景匹配度与接入成本。

## 3. 人机协作：AI 只建议，管理员裁决

AI 只做三件事，全部以**建议卡片**呈现（`src/components/AdminWorkspace.jsx` 的 `.admin-ai` 区块）：

1. **完整性检查**：缺题干/选项/答案/解析/章节/难度/关联考点 → 「待补充」标记；
2. **知识点归类建议**：给出建议章节 + 可解释理由（命中关键词），管理员一键「采纳」或手动改选；
3. **格式规范检查**：括号配平、`$` 定界符成对、占位符文本、选项数量/重复、答案范围。

**确认权设计**：
- 确认入库按钮在字段不完整时**禁用**，AI 无法绕过；
- AI 建议不改变任何数据，「采纳」也是一次显式的人工点击；
- 全系统唯一写入入口是 `addImportedQuestions(store, questions)`（`src/data/dataService.js`），只被「确认入库/全部确认」调用——**大模型在代码结构上就不存在写题库的路径**。

## 4. 后端代理与安全（server/ai-proxy.mjs）

```
前端 checkItems() ──POST /api/ai/check──▶ Vite 代理 ──▶ Node 代理(:8787) ──▶ DeepSeek API
                                                          │
                                          DEEPSEEK_API_KEY 仅存在于服务端环境变量
```

- API Key 只读 `process.env.DEEPSEEK_API_KEY`，前端 bundle 与网络面板均不可见；
- **超时 10s**（AbortController → 504），请求体上限 1MB，缺 Key 返回 503，上游失败返回 502；
- 系统提示词约束模型只输出 `{results:[{key,missing,suggestedChapterId,reason,formatIssues}]}` 建议结构；
- 启动：`DEEPSEEK_API_KEY=sk-xxx node server/ai-proxy.mjs`（开发时 Vite 已配 `/api` 代理）。

## 5. 降级逻辑（src/data/aiCheckService.js）

```js
try {
  const res = await fetch('/api/ai/check', { signal: 12s超时, ... });
  if (!res.ok) throw ...;
  return { mode: 'online', results };
} catch (e) {
  // 不抛出、不阻塞：回落到本地预置规则，建议结构与在线完全同构
  return { mode: 'offline', results: items.map(offlineSuggest), error };
}
```

- 离线归类 = 章节关键词表（命中哪个词建议哪章，理由可解释）；离线格式检查 = 确定性启发规则；
- UI 显示琥珀色「**离线演示模式**」徽标（含失败原因），管理员操作与在线完全一致；
- 工作台提供「**强制离线演示**」开关：答辩现场网络不可控时，一键锁定确定性路径；
- 已实测：代理关闭 → 502 → 自动降级，无白屏、无未捕获错误、导入流程不中断。

## 6. 答辩口径

**为什么选这个国产工具？**
「我们选 DeepSeek：一是大赛要求的国产方向，二是它在数学推理上是国产模型里的强项，而我们的场景恰好是数学题质检；三是 OpenAI 兼容接口让后端代理只有百行，十分钟就能换成通义——工具是可替换的，人机协作的架构才是我们设计的主角。」

**怎么体现"驾驭 AI 工具"？**
「我们把 AI 放在'助手'而不是'裁判'的位置：它只做完整性、归类、格式三类建议，每条建议都带可解释理由；管理员有一键采纳权也有完全修改权，字段不完整时入库按钮直接禁用——代码里唯一的写库入口只接受人工确认。同时我们做了完整的降级设计：API 超时或失败时自动切换到本地预置规则并明示'离线演示模式'，AI 挂了产品照样可用。驾驭 AI 不是让它替人做决定，而是让人始终握着方向盘、且车永远有备用动力。」

**"大模型判断不准怎么办？"**
「三层兜底：第一，AI 的输出从不直接写库，不准的建议最多停留在建议卡片上，管理员不采纳就零影响；第二，完整性检查这类关键判断用的是确定性规则而非模型，模型只负责归类建议这种'错了也无害'的环节；第三，每条归类建议都附命中关键词等理由，管理员能一眼看出它为什么这么建议、该不该信。演示时我们优先展示完整性检查——响应快、零误判，这正是我们对 AI 能力边界的刻意取舍。」

## 7. 演示动线建议

1. 打开「题库管理」→ 下载模板 → 上传预置 CSV（含 1 行错误章节 + 1 行括号不配平）；
2. 指出「待补充」标记与错误行提示（**完整性检查，确定性，首选展示**）；
3. 点「AI 辅助检查」→ 建议卡片出现（离线时徽标明示）→ 对错误行「采纳」归类建议 → 手动补全解析与考点；
4. 「确认入库」→ 关闭工作台 → 对应考点「开始做题」能抽到新题；
5. 刷新页面 → 新题仍在（持久化）。
